# DevOps / 运维工程师方案产出指南 · 领域方法论

> 本文档是 `devops-guide` 技能的领域知识库。

---

## 一、场景识别

| 场景 | 名称 | 判断条件（满足任一） | 产出量 | 预估周期 |
|------|------|---------------------|--------|---------|
| 场景一 | 0→1 基础设施搭建 | 全新项目/团队、无CI/CD、无监控、需从零配置云资源 | 10-12类 | 4-8周 |
| 场景二 | 中型运维改造/优化 | 已有基础设施新增模块、CI/CD流程改造、新增监控体系 | 6-8类 | 2-4周 |
| 场景三 | 小优化/故障修复 | 单条Pipeline修复、告警规则调整、配置变更 | 2-3类 | 1-3天 |
| 场景四 | 大版本架构迁移 | 云平台迁移、K8s版本升级、CI/CD工具链替换 | 8-10类 | 4-10周 |
| 场景五 | 技术预研/选型 | 新工具评估、新云服务PoC、成本优化方案 | 3-4类 | 1-2周 |

### 识别流程

```
是否全新项目/无基础设施？ → 是 → 场景一
    ↓否
是否云平台迁移/工具链替换/大版本升级？ → 是 → 场景四
    ↓否
是否为工具评估/成本优化方案？ → 是 → 场景五
    ↓否
是否涉及多组件改造/多环境配置/多流程变更？ → 是 → 场景二
    ↓否
→ 场景三
```

## 二、场景一：0→1 基础设施搭建（12类产出）

### 规划阶段
1. **基础设施需求分析** — 业务规模预估（QPS/DAU/数据量）、合规要求、可用性目标（3个9/4个9）、预算约束
2. **云架构设计** — 云服务选型（AWS/阿里云/腾讯云）、网络拓扑(VPC/子网/安全组)、服务部署拓扑、多区域/多AZ容灾
3. **CI/CD方案设计** — Pipeline设计（Build→Test→Scan→Deploy）、工具链选型（GitHub Actions/GitLab CI/Jenkins）、制品管理、多环境策略（dev/staging/prod）

### 实施阶段
4. **容器化方案** — Dockerfile规范（多阶段构建/镜像瘦身）、编排平台选型（K8s/Docker Compose/Nomad）、Helm Chart/Kustomize、镜像仓库策略
5. **Kubernetes配置** — Namespace规划、Deployment/Service/Ingress配置、ConfigMap/Secret管理、资源限制(Request/Limit)、HPA/VPA自动扩缩容、PodDisruptionBudget
6. **监控体系搭建** — 指标监控(Prometheus+Grafana)、日志收集(ELK/Loki)、链路追踪(Jaeger/Zipkin)、SLO/SLI定义、告警规则(分级/通知/静默)、Dashboard设计
7. **日志管理方案** — 日志格式规范(结构化JSON)、采集管道(Fluentd/Filebeat)、存储策略(热/温/冷)、保留周期、敏感信息脱敏

### 安全与运维
8. **安全加固方案** — 网络策略(NetworkPolicy)、镜像安全扫描(Trivy/Clair)、Secret加密(Sealed Secrets/Vault)、RBAC权限、Pod安全策略、审计日志
9. **灾备与高可用方案** — RPO/RTO目标、备份策略（数据库/配置/持久卷）、跨区域容灾、故障切换自动化、灾难恢复演练计划
10. **成本优化方案** — 资源规格优化(Request/Limit调优)、Spot/抢占式实例、存储分层、闲置资源识别、成本Dashboard
11. **IaC（基础设施即代码）** — Terraform/Pulumi配置、模块化设计、状态管理、变更流程（Plan→Review→Apply）
12. **运维Runbook** — 日常巡检清单、常见故障处理SOP、升级/回滚流程、值班手册

## 三、场景二：中型运维改造/优化（6-8类产出）

1. **现状分析** — 当前架构痛点、性能瓶颈、成本问题、安全风险
2. **改造方案** — 目标架构、改造成本、风险缓解
3. **CI/CD Pipeline设计** — 新Pipeline定义、与现有流程兼容、回滚机制
4. **监控告警设计** — 新增指标、Dashboard、告警规则
5. **配置变更方案** — ConfigMap/Secret变更、环境变量管理、灰度发布
6. **测试与验证** — 性能测试、混沌测试、回滚演练
7. **变更影响评估** — 上下游影响、SLA影响、回滚时间窗口
8. **操作手册更新** — 新增操作的SOP、告警响应流程

---

## 四、场景三：小优化/故障修复（2-3类产出）

1. **问题分析** — 故障现象/优化目标、根因分析、日志/监控证据
2. **修复/优化方案** — 具体配置变更、代码调整、验证步骤
3. **回归检查清单** — 关联服务验证、性能回归、告警确认

---

## 五、场景四：大版本架构迁移（8-10类产出）

1. **迁移评估报告** — 迁移动机、收益分析、风险清单、工作量评估
2. **目标架构设计** — 新架构图、新旧对比、技术栈变更
3. **数据迁移方案** — 数据库/存储迁移步骤、双写/双读过渡、一致性校验、回滚方案
4. **流量切换方案** — DNS切换/负载均衡、灰度策略（百分比/租户）、Canary Release
5. **兼容性方案** — API兼容、配置兼容、客户端影响
6. **性能基准对比** — 新旧环境QPS/延迟/资源对比
7. **测试策略** — 功能回归、性能回归、混沌工程
8. **回滚预案** — 触发条件、回滚步骤、数据回滚验证
9. **监控告警迁移** — 新旧Dashboard、告警规则迁移
10. **团队培训** — 新工具/新流程培训、FAQ文档

## 六、场景五：技术预研/选型（3-4类产出）

1. **技术调研报告** — 候选方案对比、社区活跃度、团队匹配度

## 七、DevOps 通用规范

### CI/CD Pipeline 规范
- 提交即触发：Push→Lint→Test→Build→Scan→Deploy(staging)
- 合并到 main 自动部署 staging，手动触发 production
- 制品版本：语义化版本 `v{Major}.{Minor}.{Patch}-{build_id}`
- 回滚：保留最近5个版本的制品，支持一键回滚

### Docker 最佳实践
- 多阶段构建减小镜像体积
- 非 root 用户运行
- `.dockerignore` 排除不必要文件
- 镜像标签：`{service}:{git_sha}` + `{service}:latest`
- 基础镜像优先使用 `-slim` 或 `alpine` 变体

### K8s 资源规范
| 资源 | 推荐配置 |
|------|---------|
| Request CPU | ≤ 实际用量的 60% |
| Limit CPU | = Request 或略高 |
| Request Memory | 实际用量的 1.2-1.5x |
| Limit Memory | = Request（避免OOM Kill与浪费） |
| Liveness Probe | initialDelaySeconds: 30, periodSeconds: 10 |
| Readiness Probe | initialDelaySeconds: 10, periodSeconds: 5 |
| Graceful Shutdown | terminationGracePeriodSeconds: 30-60 |

### 监控 SLO 参考
| 指标 | 内部服务 | 外部API |
|------|---------|---------|
| 可用性 | 99.9% | 99.95% |
| P95延迟 | <200ms | <500ms |
| 错误率 | <0.1% | <0.5% |
| 告警响应 | <5min(严重)/<30min(一般) | |

### 安全基线
- 镜像：每次构建自动扫描，高危漏洞阻断部署
- 网络：最小端口暴露、NetworkPolicy 默认拒绝+白名单
- 密钥：不硬编码、使用 Secret Manager / Vault、定期轮换
- 审计：API Server审计日志、kubectl操作日志、CI/CD操作日志
- 合规：等保2.0/ISO27001要求对照

## 八、产出质量检查清单

- [ ] 场景判断正确并已确认
- [ ] 架构图清晰（网络拓扑/部署拓扑/数据流）
- [ ] CI/CD Pipeline覆盖 Build→Test→Scan→Deploy 全流程
- [ ] 容器化符合最佳实践（多阶段构建/非root/资源限制）
- [ ] 监控覆盖三大支柱（Metrics/Logs/Traces）
- [ ] 告警分级明确（P0/P1/P2）+ 通知渠道 + 升级策略
- [ ] 灾备方案含 RPO/RTO + 演练计划
- [ ] 安全方案覆盖镜像/网络/密钥/审计 四个维度
- [ ] 回滚方案可执行（含数据回滚验证）
- [ ] IaC配置模块化、状态管理可控
- [ ] Runbook/操作手册可执行

### 去AI味检查
- [ ] 方案中有"如果只有 2 个人"的简化版本
- [ ] 成本预估有具体数字——不只是"使用云服务"，是"预计月费数字"
- [ ] 至少有 1 处"业界标准做法ABC在我们场景下只用A就够了"的判断
- [ ] 监控告警不是堆指标——每个告警都经过了"半夜被叫起来值不值得"的测试

## 十、超越AI味：运维工程师的真实经验

> AI 能画出完美的 K8s 架构，但真正的运维知道——架构是月费的账单，凌晨的告警，和必须在 5 分钟内恢复的服务。

### 10.1 反AI运维决策五条

**1. 从"需要什么"开始，不要从"K8s"开始**

- 错误做法: "部署方案：K8s集群 + Istio + Prometheus + Grafana + ELK"
- 正确做法: "当前 3 台服务器、日活 5000。Docker Compose + Nginx 反向代理够用。K8s 运维成本远超当前收益，等日活到 5 万再考虑"

**2. CI/CD 不是越复杂越好**

- 错误做法: 20 个 Stage 的 Pipeline
- 正确做法: "Push -> lint+test(并行) -> build -> deploy staging -> 人工确认 -> deploy prod。团队不到 5 人，staging 可以跳过直接 deploy prod（feature flag 控制灰度）"

**3. 告警要经过"半夜测试"**

- 只告警影响用户的事：支付接口 P95>3s 持续 5 分钟、错误率>1% 持续 3 分钟、磁盘>90% 预测 2 小时内满。其他指标只做 Dashboard——半夜被叫起来必须是真的出事了

**4. 备份不验证 = 没有备份**

- "每月 1 号从最新备份恢复->跑数据校验脚本->验证业务关键流程->输出恢复报告。恢复时间 > 预期 RTO 则告警"

**5. 成本没有意识 = 运维没有价值**

- "当前方案月费预估：3 台 4C8G ¥2,400 + RDS ¥800 + Redis ¥400 + 带宽 ¥300 = ¥3,900/月。优化方案：spot 实例可降 ¥600/月"

### 10.2 运维经验法则

| 原则 | 说明 |
|------|------|
| 3 人以下团队 | 别上 K8s，Docker Compose + Ansible 够用 |
| 没有 oncall 轮值 | 不要设凌晨告警——没人看等于没设 |
| 灾备方案 | 必须在文档写完之后实际演练一次 |
| 每次事故 | 必须有 postmortem：发生了什么->为什么发生->怎么不再发生 |

---

_运维的价值 = 少花钱、少出事、出了事能 5 分钟恢复。_
