## 一、运维核心四使命 + 关键规则

**四使命**：①可靠性（99.9%+ 可用性）②成本优化 ③安全合规 ④可扩展架构。

**关键规则**：
1. **先监控后变更**——任何基础设施变更前先有监控
2. **备份恢复必须"测过"**——有测试过的恢复流程才算数（呼应 mvp-devops 蒸馏"每月验证"）
3. **所有变更文档化**——含回滚流程 + 验证步骤
4. **安全内建**——所有基础设施变更默认过安全加固 + 合规校验

---

## 二、监控告警量化规则（阈值基线）

| 告警 | 触发表达式（语义） | 持续 | 级别 |
|------|-------------------|:---:|------|
| CPU 高 | CPU 使用率 > 80% | 5min | warning |
| 内存高 | 内存使用率 > 90% | 5min | **critical** |
| 磁盘低 | 磁盘使用率 > 85% | 2min | warning |
| 服务宕 | 采集目标 up == 0 | 1min | **critical** |

**采集频率分级**：基础设施 30s / 应用 15s / 数据库 30s——不是全部 15s（省资源）。
**告警分层**：基础设施规则（CPU/内存/磁盘/网络）× 应用规则（错误率/延迟）× 业务指标（转化/订单——业务挂了比服务器挂了更早被发现）。

## 三、备份自动化完整方案（加密 + 异地 + 验证 + 清理）

**七要素**（缺一不算完整的备份系统）：
1. **加密**：gpg AES256 对称加密（s2k 强哈希），密钥文件不落脚本
2. **异地**：本地保留 + 上传对象存储（STANDARD_IA 降本）
3. **验证**：每次备份后解密校验完整性（gpg --decrypt 成功才算数）
4. **清理**：保留 30 天自动清理（本地 find + 远端生命周期策略双保险）
5. **通知**：成功/失败都推送（失败 webhook 告警——**webhook URL 用环境变量，绝不进版本库**）
6. **错误处理**：`set -euo pipefail` 防静默失败 + 失败即通知
7. **覆盖范围**：数据库（pg_dump）+ 文件系统（上传目录/配置/日志）分层备份

## 四、IaC 纪律（基础设施即代码）

- **state 远程 + 加密 + 锁**：Terraform state 存远程（S3）且 encrypt，配 DynamoDB 锁防并发（或等价方案）
- 资源全部打 tag：`Name`/`Environment`/`Owner`（成本归因 + 运维定位的前提）
- **数据库实例基线**：加密存储 + 备份保留 ≥7 天 + 定时备份窗口 + 维护窗口错峰 + 增强监控开启 + `skip_final_snapshot=false`（删库留终快照）
- 扩缩容用模板/组（launch template + ASG），`create_before_destroy` 避免替换窗口停机
- 变更走版本控制（代码 review → 计划 → 执行 → 验证）

## 五、基础设施健康报告模板（给管理层的"人话"）

```markdown
# 基础设施健康与性能报告
## 执行摘要
- 可靠性：可用性 XX%（目标 99.9%）/ MTTR X 小时（目标 <4h）/ 事件数（环比）
- 成本：月成本 ¥X（±%）/ 单用户成本 / 优化节省
- 行动项：Critical（立即）/ Optimization（优化）/ Strategic（战略）

## 详细分析
- 系统性能（CPU/内存/存储/网络 平均+峰值）
- 可用性（各服务 uptime / 错误率 / 响应时间 / MTTR-MTBF）

## 成本分析
- 支出拆分（计算/存储/网络/第三方）+ 优化机会（right-sizing/预留/自动化）

## 建议
- 立即（7 天）：性能/安全/成本快赢
- 短期（30 天）：监控增强/自动化/容量
- 战略（90+ 天）：架构演进/技术升级/容灾
```
